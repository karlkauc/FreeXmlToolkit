XsdDoc Tags

JavaDoc-style annotations in xs:appinfo — how FreeXmlToolkit reads, renders and edits them, in the HTML documentation generator and in the XSD editor.

Analysis of the code base · 2026-09-09 · FreeXmlToolkit

1. Where the metadata lives

Everything structured hangs off xs:annotation with its two children:

  • xs:documentation — human-readable prose, multi-language via xml:lang.
  • xs:appinfo — machine-readable metadata. Its source attribute carries the JavaDoc-style tag.

2. The specially handled tags

TagMeaningHTML documentationXSD editor (Inspector)
@since Schema version that introduced the component “Since” field in the JavaDoc block Text field @since
@see Cross reference; may occur several times “See Also” list, {@link} resolved to hyperlinks List with Add/Remove + {@link} autocomplete
@deprecated Deprecation marker plus reason Red warning box at the top of the detail page “Deprecated” checkbox + note field
@version Version detail of the component Only under “Additional Information” Text field @version
@author Author Only under “Additional Information” No field — but preserved unchanged on edit
{@link XPath|Name} Inline link inside @see / @deprecated <a href> to the target's detail page Autocomplete popup over the schema's element paths
altova:exampleValues Example values (FundsXML convention) “Sample Data” on the detail page “Example values” list; also feeds sample-XML generation and IntelliSense
@sourceFile / fxt:sourceFile Records which included file a component came from when a multi-file schema is flattened (details) — Internal; passed through untouched
anything else Arbitrary source string or text content “Additional Information” section (HTML-escaped) Preserved untouched

On top of that, xs:documentation/@xml:lang gets special treatment: it drives the language switcher on the generated pages, the “Scan languages” filter of the documentation generator, and one row per language in the Inspector.

3. Example

<xs:element name="Transaction">
    <xs:annotation>
        <xs:documentation xml:lang="en">A single financial transaction.</xs:documentation>
        <xs:documentation xml:lang="de">Eine einzelne Transaktion.</xs:documentation>

        <xs:appinfo source="@since 4.0.0"/>
        <xs:appinfo source="@version 1.2"/>
        <xs:appinfo source="@see {@link /FundsXML4/ControlData}"/>
        <xs:appinfo source="@see {@link TransactionType}"/>
        <xs:appinfo source="@deprecated Use {@link /FundsXML4/NewTransaction} instead."/>
        <xs:appinfo>
            <altova:exampleValues xmlns:altova="http://www.altova.com/xml-schema-extensions">
                <altova:example value="TRX-0815"/>
            </altova:exampleValues>
        </xs:appinfo>
    </xs:annotation>
</xs:element>
{@link} resolution: the target may be an absolute XPath (/FundsXML4/ControlData — synthetic CHOICE_n / SEQUENCE_n path segments are stripped before matching) or a plain element name (first match wins). A target that cannot be resolved degrades to plain <code> text instead of failing the build.

5. fxt:sourceFile — origin tracking when flattening

This is the toolkit's own xs:appinfo extension, in the namespace http://freexmltoolkit.org/schema/flattening (prefix fxt). It answers a question that flattening otherwise destroys: which of the included files did this component come from?

Who writes it

SchemaResolver.addSourceFileAppinfo(), while merging xs:include content into the main document — but only when the parse options ask for it (XsdParseOptions.addSourceFileAsAppinfo, default false). The marker is attached to top-level constructs only: xs:element, xs:complexType, xs:simpleType, xs:group, xs:attributeGroup, xs:attribute. A missing xs:annotation is created as the first child (as the XSD spec requires), and the fxt prefix is declared once on xs:schema.

<xs:complexType name="PersonType">
    <xs:annotation>
        <xs:appinfo>
            <fxt:sourceFile xmlns:fxt="http://freexmltoolkit.org/schema/flattening">types.xsd</fxt:sourceFile>
        </xs:appinfo>
    </xs:annotation>
    ...
</xs:complexType>

Who reads it

  • XsdModelAdapter recognises the element and stores it as a synthetic @sourceFile <filename> tag — which is why @sourceFile shows up as a tag in the appinfo statistics.
  • XsdNodeFactory keeps it as raw XML like any other complex appinfo content.
  • XsdAppInfo.toXmlStrings() has a dedicated branch for the @sourceFile tag: it regenerates a clean fxt:sourceFile element carrying only xmlns:fxt, instead of dragging along every namespace the node inherited (altova, ds, vc, …).
  • The Inspector never shows or edits it, but AppInfoFieldsEditor carries it over untouched on every commit, so editing @since on a flattened component does not lose its origin marker.
Not to be confused with the editor's own origin tracking. Per-file node counts in the Statistics view, the “which file is dirty?” logic in XsdEditorContext, and the file column of the quality issues all use the in-memory XsdNode.getSourceInfo() / IncludeSourceInfo, not this appinfo. They work on any multi-file schema, flattened or not. fxt:sourceFile is the persisted counterpart: it is the only form of origin information that survives writing the flattened schema to disk and reopening it.

Status

Writing the marker is currently an API-level option: the shell's Flatten Schema dialog (FlattenOptionsDialog → FlattenOptions → SchemaFlattenTransformer) does not offer it, and no production code sets addSourceFileAsAppinfo(true) — only XsdFlatteningSourceFileTrackingTest does. Reading, preserving and re-serializing the marker is always active, so schemas that carry it round trip correctly.

6. Findings

1. Source-only xs:appinfo never reached the editor modelfixed

The documented (and, in FundsXML4.xsd, ubiquitous) form is a self-closing element whose whole payload sits in the source attribute:

<xs:appinfo source="@since 4.2.8"/>

Both model parsers dropped it:

  • XsdNodeFactory had no else branch for appinfo without text content.
  • XsdModelAdapter called addEntry(source, ""), and XsdAppInfo.addEntry() discards entries with empty content.

Effect: the generated HTML documentation showed “Since 4.2.8” (it reads the source attribute directly), while the Inspector showed an empty @since field for the same node — and saving the file dropped the tag.

Fix: both parsers now fall back to the source attribute as the entry content when the element has no text content, so the tag is parsed exactly as it is for the text-content form:

  • XsdNodeFactory.parseAnnotation() — new else if branch appInfo.addEntry(source, source).
  • XsdModelAdapter.parseAnnotation() — addEntry(source, "") replaced by addEntry(source, source).

2. The editor wrote every tag twicefixed

XsdAppInfo.toXmlStrings() emitted the tag both as the source attribute and as text content:

<xs:appinfo source="@since 4.2.8">@since 4.2.8</xs:appinfo>

That round-trips and is read correctly by the documentation generator, but it deviates from the documented form and inflates every edited schema.

Fix: toXmlStrings() now writes a self-closing element whenever the text content would merely repeat the source attribute (XsdAppInfo.isSourceOnly()). An entry whose text differs from its source — or that carries raw XML such as altova:exampleValues — keeps its content unchanged:

<xs:appinfo source="@since 4.2.8"/>
<xs:appinfo source="urn:example:tooling">generated by the mapping tool</xs:appinfo>

7. Tests

XsdAppInfoSourceOnlyTest (controls/v2/model/) covers both fixes: parsing a source-only appinfo through XsdNodeFactory and through XsdModelAdapter, the self-closing serialization of the managed tags, the preservation of distinct text content, and a parse → serialize round trip.

./gradlew test --tests "org.fxt.freexmltoolkit.controls.v2.model.XsdAppInfoSourceOnlyTest"
